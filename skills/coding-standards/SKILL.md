# Coding Standards

按语言组织的编码口径规则库。设计阶段、编码阶段、review 阶段共用同一份规则，判定与定级口径一致。

## 选文件

先判定**本次改动涉及的语言**，再读对应文件。改动横跨多语言时逐个读。不要用一个仓库里的主导语言去推断某个子模块。

| 语言 | 文件 | 识别依据 |
| --- | --- | --- |
| Java | `references/java.md` | `pom.xml`、`build.gradle`、`*.java` |
| Python | `references/python.md` | `pyproject.toml`、`requirements*.txt`、`setup.py`、`*.py` |
| TypeScript | `references/typescript.md` | `tsconfig.json`、`package.json`、`*.ts`、`*.tsx` |
| Vue | `references/vue.md` | `*.vue`、`vite.config.*`、`nuxt.config.*` |

尚无对应文件的（该语言还没沉淀规则）：只应用下面的通用部分，并**明说缺少该语言的规则文件**，不要凭印象替它定规则。

## 通用：设计模式按需，不强制

**简单需求直接实现。** 不为了「像设计」而抽抽象层，也不为了用模式而用模式。多写几个类、多一层接口，如果只有一条分支在跑，就是净负担。

**触发条件**——满足任一条，才需要评估模式（策略 / 工厂 / 责任链 / 模板方法 / 状态）：

- 同一业务判断维度上 `if / else if` 分支**超过 3 个**（即 4 个及以上），或等价的多路 `switch`
- 同一维度上已确认还会有新分支加入（同一迭代或下个迭代），会持续加
- 分支数量未超阈值，但每个分支都带实质逻辑（不是单行赋值或取值映射），堆成一个长方法

不满足触发条件：直接实现，在设计说明里写一句「分支未达阈值，直接实现」即可，不需要论证为什么不用模式。

满足触发条件：说明变化维度是什么、用哪个模式吸收、否掉了哪些替代方案、复用了工程里哪个既有抽象而不是新造一套。

**不变量**（与阈值无关，始终成立）：禁止靠反复修改稳定的核心抽象来加业务分支，应改为扩展。

**定级**：

- 超过阈值、分支内有实质逻辑，仍堆在一个方法里 → `P2`
- 超过阈值，但只是枚举到值的单行映射 → `P3` 或按项目已有惯例（查表、`Map`、枚举自带行为）处理，不强行上模式
- 分支未超阈值、也能直接实现，却被强加了抽象层（接口只有一个实现且无第二实现） → `P3`
- 靠反复修改稳定核心类来加业务分支 → `P2`

## 通用：其余两项结论

设计与编码前，除设计模式外的两项仍要给出结论，写在设计说明里，「没有」也要显式写：

1. **并发模型**：谁在跑这段逻辑，哪些部分并行或异步，是否落在事务/请求上下文内，失败与超时怎么处理，上下文（事务、`ThreadLocal`、MDC、租户、安全上下文）怎么传到工作线程或异步任务。无线程、无异步就写「无并发」。
2. **语言惯用法**：用到了哪些该语言的惯用写法，哪里刻意保留了显式循环或等价手工写法，为什么。

## 通用：新代码强制，存量记账不阻断

- 规则的作用面是**本次改动新增或修改的行**。这是可执行、可判定的边界。
- 改动没碰到的既有代码属存量欠账：**不得报 `P0`/`P1`/`P2`，也不要求本 MR 修**；最多记一条 `P3`，前缀 `存量`，让欠账可见但不阻断合并。
- 例外是「顺着存量继续错」：往不安全的老写法里加新调用方、新增未处理的并发、新增未判空的取值——这些落在改动行上，按正常严重度报。

## 与工程既有规范的关系

本技能不替代工程自己的规范。仓库已有 spec、团队共享 skill 优先；冲突时以工程规范为准，并说明冲突点。本技能只补它们没写清的部分。

## 自查清单

动手前或提 MR 前，按改动范围过一遍。各语言的 grep 清单在该语言文件末尾。
