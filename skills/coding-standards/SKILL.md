# Coding Standards

按语言组织的编码口径规则库。设计阶段、编码阶段、review 阶段共用同一份规则，判定与定级口径一致。

## 选文件

先判定**本次改动涉及的语言**，再读对应文件。改动横跨多语言时逐个读。不要用一个仓库里的主导语言去推断某个子模块。

| 语言 / 框架 | 文件 | 识别依据 |
| --- | --- | --- |
| Java | `references/java.md` | `pom.xml`、`build.gradle`、`*.java` |
| Python | `references/python.md` | `pyproject.toml`、`requirements*.txt`、`setup.py`、`*.py` |
| JavaScript | `references/javascript.md` | `*.js`、`*.mjs`、`*.cjs` |
| TypeScript | `references/typescript.md` | `tsconfig.json`、`*.ts`、`*.tsx`；有 tsconfig 的工程里 `.js` 同样适用 |
| Vue | `references/vue.md` | `*.vue`、`vite.config.*`、`nuxt.config.*` |
| React | `references/react.md` | `package.json` 依赖 `react`、`*.jsx`、`*.tsx` |

改动横跨语言与框架时逐个读（例：改一个 Vue 组件且工程是 TS，读 `vue.md` + `typescript.md`）。

尚无对应文件的（该语言还没沉淀规则）：只应用下面的通用部分，并**明说缺少该语言的规则文件**，不要凭印象替它定规则。

## 通用：设计模式准入

**准入标准与语言无关，各语言共用这一节。** 落地手段（用什么语法、什么框架机制实现）看对应语言文件。

**默认不引入。** 遵守 YAGNI 与 KISS。简单需求直接实现，不为「像设计」抽抽象层，也不为用模式而用模式——只有一条分支在跑时，多写几个类、多一层接口就是净负担。

### 准入矩阵

矩阵是「严禁 vs 必须」的场景判定，与语言无关。

| 模式 | 严禁（直接平铺代码） | 必须（触发设计模式） |
| --- | --- | --- |
| 策略 Strategy | 仅 2 个分支，或分支体只有几行（单分支 < 10 行且不含 IO/事务） | 同一判断维度 **≥ 3 个**独立分支且分支内有实质逻辑，或已确认会持续扩展 |
| 建造者 Builder | 属性 < 5 个，或绝大多数为必填 | 属性 ≥ 5 个且多数字段可选，且需要不可变对象 |
| 单例 Singleton | 无状态工具类、仅为省内存（这类应是模块级函数或框架组件） | 全局唯一的有状态管理器、线程池、连接代理 |
| 工厂 Factory | 直接构造 + 赋值就能完成的普通数据对象 | 构造过程复杂：组合多源数据、读配置、有前置流水线 |
| 模板方法 Template | 仅 1–2 行相似；为抽象而造基类导致继承层级过深 | 多个流程主骨架一致，仅一两个子步骤有差异 |

### 触发条件（可数、可查）

同一业务判断维度上满足任一条，才评估模式：

1. 分支数 **≥ 3**（`if / else if`、多路 `switch`、等价的条件分派）
2. 该维度**已确认**新分支会在同迭代或下一迭代加入（是已排期的实现，不是「可能会扩展」的预测）
3. 分支数未达阈值，但单个分支体超过 10 行实质逻辑，堆成一个长方法

不满足：直接实现，设计说明写一句「分支未达阈值，直接实现」，不需要论证为何不用模式。

满足：说明变化维度是什么、用哪个模式吸收、否掉了哪些替代方案、复用了工程里哪个既有抽象而不是新造一套。

### 始终成立

阈值只决定「要不要评估模式」，不改变这一条：**禁止靠反复修改稳定的核心抽象来加业务分支，应改为扩展。**

### 定级

- 分支 ≥ 3、分支内有实质逻辑，仍平铺在一个方法里 → `P2`
- 分支 ≥ 3 但只是取值到结果的单行映射 → `P3`，或按既有惯例用查表 / 映射表 / 枚举行为，不强推模式
- 未达阈值、能直接实现却被强加抽象层（接口或基类只有一个实现且无第二实现）→ `P3`
- 靠反复修改稳定核心类来加业务分支 → `P2`
- 绕过工程既有抽象、另造重复机制 → `P2`

### 审查记录的位置

模式准入结论（是否引入、引入了什么、触发条件如何满足）写进**设计说明或 MR 描述**，不写进源码注释。源码注释只解释业务意图与不显然的决定，过程性元信息对后来读代码的人没有长期价值。

## 通用：其余两项结论

设计与编码前，除设计模式外的两项仍要给出结论，写在设计说明里，「没有」也要显式写：

1. **并发模型**：谁在跑这段逻辑，哪些部分并行或异步，是否落在事务/请求上下文内，失败与超时怎么处理，上下文（事务、`ThreadLocal`、MDC、租户、安全上下文）怎么传到工作线程或异步任务。无线程、无异步就写「无并发」。
2. **语言惯用法**：用到了哪些该语言的惯用写法，哪里刻意保留了显式循环或等价手工写法，为什么。

## 通用：重构准入

**定义**：重构 = 外部可观察行为不变的结构调整。可观察行为包括返回值、异常类型、状态副作用、日志级别与对外调用次数。行为变了就不是重构，是功能改动，按功能改动审。

### 坏味道识别

下面是「这段代码该不该重构」的识别信号。阈值是**参考值**，不是强制线——超过阈值先看是否真有维护痛点，没有就不动（见「完成标准」）。

| 坏味道 | 识别信号（参考阈值） | 手法 |
| --- | --- | --- |
| 长方法 | 超过 80 行，或嵌套超过 3 层 | 提取方法 |
| 长参数列表 | 超过 5 个参数，或同几个参数总是一起出现 | 引入参数对象 |
| 大类 / 上帝类 | 超过 500 行，或承担 3 个以上不相关职责 | 提取类、搬移职责 |
| 重复代码 | 同一逻辑出现 3 次以上 | 提取共享方法或工具 |
| 发散式变化 | 一个类因多个不相关的需求被反复修改 | 按变化原因拆分 |
| 霰弹式修改 | 一个需求要改 5 个以上类 | 合并职责、收敛入口 |
| 依恋情结 | 方法访问另一个类的数据多于本类 | 搬移方法到数据所在处 |
| 数据泥团 | 3 个以上字段总是成组出现 | 提取对象 |
| 基本类型偏执 | 金额、时间、ID 用裸 `String` / `long` 表达 | 用既有类型（`BigDecimal`、时间类型、ID 值对象） |
| 临时字段 | 字段只在一个方法的生命周期内有意义 | 降为局部变量或参数对象 |
| 死代码 | 注释掉的代码块、无调用方的方法、不可达分支 | 直接删除（版本控制留有历史） |

**识别信号的用途是提示，不是判决**。坏味道落在别人没碰的存量代码里 → 记 `P3` 前缀 `存量`，不阻断；落在本 MR 改动行上、或满足下面的顺手重构触发条件 → 按 `P2` 要求处理。

「以显式替换隐式」在 Java 里就是补 Javadoc / `@Schema`，那是本工程注释规范的范围，不在这里重复。

### 默认不做无关重构

- 本 MR 只动需求相关代码。顺手看到别处的坏味道，记一条 `P3` 前缀 `存量`，不在本 MR 展开。
- 未经说明的整包 / 全仓重构，即使每一步都对，也按 `P2` 报：review 无法在合理时间内验证，出问题回滚会把需求一起带走。

### 该顺手重构的触发条件（rule of three）

满足任一条就在本 MR 里做，范围限定在当事函数 / 类：

- 同一段逻辑在本 MR 里被**第三次**复制
- 本 MR **第三次**修改同一处代码（说明这处结构已不适配变化）
- 不复用就会把需求逻辑散落在两处以上、后续必然改错

### 安全前提

- 改结构前，被改行为要有能跑起来的测试覆盖；没有就先补特征测试（characterization test），确有理由跳过时在设计说明与 MR 中写明风险与验证手段。
- **高风险路径**（金额、账户、权限、数据隔离、事务、幂等、回调）不允许无测试的结构重写。

### 必须拆开

- 重构与行为改动**分提交**，至少分 commit，能分 MR 更好。同一 commit 混两者 → `P2`：review 分辨不出哪一行改变了行为，回滚粒度也没了。
- 纯格式化、纯重命名、批量注释重写这类海量 diff 必须独立提交并声明无逻辑变更；夹进功能提交 → `P2`。批量重写无关历史注释另按工程 spec 的注释规则处理。

### 定级

- 同一 commit 混重构与行为改动 → `P2`
- 借需求之名做无关的大范围重构 → `P2`
- 改了可观察行为却声明为重构（异常类型、返回结构、日志级别等）→ `P2`，按功能改动重审
- 高风险路径无测试的结构重写 → `P2`
- 该顺手重构却把同一逻辑复制第三遍 → `P2`
- 无关的坏味道记账 → `P3` 前缀 `存量`，不阻断

## 通用：重构手法目录

手法本身与语言无关，具体语法映射见各语言文件。一次只做一类手法——混着做，review 分不清哪一步改变了行为。

### 结构类

- **提取方法**：长方法里某几行有独立意图或可命名时，提取并取一个说明「做什么」而非「怎么做」的名字。
- **提取类 / 搬移职责**：类内出现两组不相关的字段与方法时，按职责拆开并搬到数据所在处。
- **内联**：方法与间接层只被一处调用、且不表达额外语义时，合回调用处。
- **引入参数对象**：同几个参数在多处一起传递时，合成参数对象。
- **以对象替换数据值**：金额、时间、ID、状态等裸值换成语义类型。

### 逻辑类

- **以多态 / 映射替换条件分派**：同一判断维度分支 ≥ 3 且分支内是实质逻辑时，用多态、映射表或枚举行为替换 `if / else if` 链——注意这与设计模式准入门槛是同一条规则，不是两套。
- **以管道替换循环**：循环只做遍历 + 收集 / 转换 / 聚合时，换成管道（Java 的 Stream）。保留显式循环的场景见各语言文件。
- **拆分循环**：一个循环里做互不相关的两件事时，拆成两个循环，各自可读。
- **合并重复分支**：多个分支体相同或只差一个常量时，合并并抽出差异。
- **以查询替换临时变量**：临时变量承载的是一段可重复计算的表达式时，改成查询方法。
- **删除死代码**：注释掉的代码、无调用方的方法、不可达分支直接删；版本控制里有历史，不需要留在源码里当注释。

### 反向动作

重构不只是拆。**抽象层只有一条实现、且没有确认的第二条时，把它合回去**——多余的接口、工厂、包装类都是净负担。这与设计模式准入的「未达阈值不引入抽象层」是同一条规则的两个方向。

## 通用：完成标准

- **坏味道消失即停**，不追求结构「完美」。为了命中某个阈值把清晰的代码改成绕的，是反向损害 → `P3`。
- 重构后如果方法数、类数显著增加而可读性没有提升，要在设计说明里给出理由，否则视为过度设计 → `P3`。
- 重构的验收是**行为未变 + 测试仍通过**。纯结构调整也必须跑受影响范围的最小验证；跑不了要写明原因与替代验证手段。
- 重构完成的那次提交里不应出现新的业务分支——出现就说明混进了行为改动，回到「必须拆开」。

## 通用：新代码强制，存量记账不阻断

- 规则的作用面是**本次改动新增或修改的行**。这是可执行、可判定的边界。
- 改动没碰到的既有代码属存量欠账：**不得报 `P0`/`P1`/`P2`，也不要求本 MR 修**；最多记一条 `P3`，前缀 `存量`，让欠账可见但不阻断合并。
- 例外是「顺着存量继续错」：往不安全的老写法里加新调用方、新增未处理的并发、新增未判空的取值——这些落在改动行上，按正常严重度报。

## 优先级

冲突时按此顺序取舍，高者覆盖低者，并说明冲突点：

1. **公司共享技能库**（`duyan-backend-standards` 等）——**优先级最高**
2. **工程 spec**（`.trellis/spec/`、仓库 `AGENTS.md` / `CLAUDE.md`）
3. **本技能**

本技能起补位作用：只补上面两级没写清的部分，不推翻它们已明确的结论。若本技能与公司共享库冲突，以共享库为准；发现冲突要指出来，而不是默默按本技能执行。

动手前或提 MR 前，按改动范围过一遍。各语言的 grep 清单在该语言文件末尾。
